01 // ARQUITECTURA

Tres piezas, un camino

La CLI nunca habla directo con el proveedor de IA. Todo pasa por el servidor: él guarda la API key, elige el modelo permitido y devuelve solo la respuesta. Cambiá entre despliegue local y Cloudflare — el código del handler es el mismo.

02 // SERVIDOR + WORKER

Un handler, dos cuerpos

worker/src/handler.ts es el corazón: una función handleRequest() que recibe una Request estándar. El servidor local la monta sobre Node http; el Worker de Cloudflare la exporta tal cual. Misma lógica, cero duplicación.

POST/

El chat. Body {prompt, model} → valida, consulta al proveedor y devuelve {reply, model}.

GET/models

Proveedor, modelo por defecto y lista blanca. También protegido por token.

GET/health

Latido: {ok:true, provider}. Ideal para verificar que el server vive.

GET/download?platform=

Entrega el updater según el SO de la CLI. El server no decide nada: siempre envía el archivo.

▶ Pipeline de una petición

  1. 01Llega la request · OPTIONS responde CORS
  2. 02Authorization: Bearer <token> — se valida ANTES de cualquier GET
  3. 03Rate limit: rl:<ip>:<fecha> en KV · tope DAILY_LIMIT/día → 429
  4. 04Validaciones: prompt ≤ MAX_PROMPT_LENGTH · modelo ∈ lista blanca
  5. 05provider.complete() → Gemini u OpenAI-compatible
  6. 06Errores mapeados: 429 cuota · 401/403 clave · 404 modelo
  7. 07JSON {reply, model} de vuelta a la CLI ✅
¿Por qué el token va antes de los GET? Sin eso, /health y /models le dirían a cualquiera con la URL qué proveedor y modelos usás.

04 // EL PUERTO

"El ping funciona… pero el chat se cuelga"

El servidor local escucha en todas las interfaces (0.0.0.0:8787), así que en teoría toda la LAN puede usarlo. Pero entre el servidor y tu otra máquina hay un firewall. Y acá está la trampa: ping usa ICMP, el chat usa TCP. Son cosas distintas.

05 // UPDATER

El ciclo de vida del updater

Idea clave: el servidor no decide nada. /download siempre envía el archivo; la lógica de "hay versión nueva, descargá, instalate" vive dentro del propio script que recibe la CLI. El server puede cambiar de VM en cualquier momento y el ciclo mantiene al cliente fresco sin reiniciar nada.

flujo común — 4 pasos
① GET /download?platform=linux · Bearer token · timeout 30s
▶
② Guardar~/.lexema/updates/update.elf
▶
③ chmod 755listo para ejecutar
▶
④ Ejecutar.sh → bash · elf/exe → directo

⚡ Modo one-shot: descargar, correr, morir

  1. 01El comando arranca → updater en background (no bloquea la respuesta)
  2. 02Verbose solo la 1ª vez y en lexema update: los ciclos del loop son silenciosos
  3. 03Descarga + guarda + ejecuta con timeout de 15s
  4. 04¿Colgado? SIGKILL al grupo completo de procesos (pid negativo)
  5. 05stdout/stderr SIEMPRE se muestran: es el canal de notificaciones
  6. 06Si no hay red/server: warning amarillo, la CLI sigue normal

¿Por qué matar al grupo?

Un sleep hijo del script hereda el pipe de stdout y mantiene vivo el event loop aunque el hijo muera. Por eso el kill va al grupo entero (kill(-pid, SIGKILL)) y se destruyen los pipes.
Nunca trava la CLI: descarga con AbortController, ejecución con timeout — un updater roto es un warning, no un cuelgue.

📁 Dónde vive

~/.lexema/updates/ — se crea solo. Filename real desde Content-Disposition, saneado con basename().

updater (daemon)detach · grupo propio · sin timeout loop: 30s · unref

♾️ Modo daemon: vive mientras la sesión

  1. 01lexema chat arranca → corrida inmediata (verbose)
  2. 02launchUpdaterDetached: proceso aparte, sin timeout — pensado para quedarse vivo
  3. 03Su stdout/stderr se muestran en vivo dentro de la sesión
  4. 04Cada 30s: ¿sigue vivo? sí → no hacer nada
  5. 05¿Murió? → relanzar (la VM del server pudo cambiar)
  6. 06Al cerrar sesión: clearInterval + abort descarga + SIGKILL grupo

Detalles finos que salvan la vida

Timer unref'eado: el loop de 30s no mantiene vivo el proceso por sí mismo. Si el usuario sale, la CLI puede morir ya.
No solapar: si ya hay un ciclo de descarga en vuelo o un daemon corriendo, el tick no hace nada. Un updater, una vida.
Salida limpia: stopUpdaterLoop() mata todo lo en vuelo y espera el asentamiento — al morir los procesos, sus promesas resuelven de inmediato.

06 // DISTRIBUCIÓN

Del tag al curl | bash

Publicar es pushear un tag. GitHub Actions compila para 4 plataformas, firma los binarios de macOS y arma el Release. Los instaladores apuntan al repo — costo total de infra: $0.

🏷️ git tag v1.0.2push origin v1.0.2
▶
⚙️ GitHub Actionsrelease.yml se dispara
▶
📦 4 binarioslinux-x64 · macos-x64 · macos-arm64 · win-x64.exe
▶
🚀 GitHub Release+ inyección del token compartido
▶
⬇️ install.sh / ps1curl fsSL … | bash
macOS: los binarios se compilan en un runner macos-latest y se firman con codesign --sign - (ad-hoc). Sin eso, macOS mata el ejecutable al abrirlo. Si compilás vos en Linux, necesitás firmar desde un Mac o instalar ldid.
Dominio propio (opcional): copiás install.sh / install.ps1 a cualquier hosting estático (p.ej. Cloudflare Pages) y tus usuarios instalan desde tu dominio. El instalador ya apunta al repo de releases.
